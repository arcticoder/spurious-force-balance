# KB: why the main board is slow, and the plan (assessment 2026-11-11, no action taken)

Audience: future LLM sessions. Read before touching `hardware/instrument/layout/`. The plan items are in `TODO-agent.md` (section "Main board: change of method"); the user's scope decision is task 6 in `TODO-arcticoder.md`.

## What the board is
164 parts, 111 nets, 4 layers, 120 x 90 mm, about ten functional blocks on one PCB: USB-C entry with fuse and ESD; two LP5907 3.3 V rails; RP2040 with QSPI flash and crystal; I2C (TMP117, LIS2DW12 on board, two JST-SH to sensor heads); MCP4728 DAC; ADS131A04 24-bit ADC with its own crystal and reference; two LED current sinks; a 0.3 A device-current sink (AOD4184A, TO-252); an MT3608 24 V boost and filter; an OPA197 plate driver; two coin-motor drivers; 15 connectors on three edges. A typical first board is 30-60 parts with one or two of these concerns; this one mixes precision analog (24-bit ADC, pA-level photocurrents through the heads), a switching boost, a power FET and USB.

## Why it is slow (in order of weight)
1. **No human-quality placement.** `place()` is a generic force-directed pass with a repulsion legalisation. It knows nets, not signal flow, data-sheet layouts or the analog/digital partition. Routability, the Y-branches, the unrouted connections, the L4 courtyard overlaps and the USB-C via short all follow from placement. Every later fix is downstream patching.
2. **Everything goes through an autorouter, all at once.** Freerouting routes all 415 connections in one run of 9-60 minutes (2026-11-08: 9 min; 2026-11-10: 15-25 min; 2026-11-11: 35 min with no result, then a 58-minute run). A run that hits the limit writes nothing, so a failed run costs its full length and teaches little. Critical nets (USB pair, crystals, power trunks, ADC inputs) get no special treatment.
3. **Two inner planes on 4 layers leave 2 signal layers for about 100 signal nets.** The In2 3V3_D plane experiment removed a routing layer from a board that already needed In2 for signals (100 x 80 with only In1 as a plane left 156 connections unrouted). The conventional 4-layer stackup is signal / GND / power pours plus slow signals / signal, not two solid planes.
4. **Rebuilding KiCad in Python.** `pcbnew` segfaults headless on `LoadBoard` (KiCad 9.0.9), so the pipeline uses kiutils plus a hand-written DSN writer and SES importer, and each KiCad feature needed (zones, holes, silk policy, library sync, rules, acute-joint repair) became new code with new bugs (the GrText crash in `write_dsn` on 2026-11-11). The cause of the segfault was never investigated.
5. **Rules arrived one at a time.** Planes (11-10), DRC floors and the pad-hole rule, mounting holes, silk policy and the netlist-parity check (all 11-11) were added after routing had started, and several of them change what the router must do, so each one forced another full run. There was no written layout specification before the first route.
6. **Session time is shared.** WP5 work is interleaved with print sessions, orders and documentation in the same chats; a 30-60-minute route blocks a session or is left running between turns.

## What would improve it (the plan, smallest change first)
- **A. Diagnose the `pcbnew` segfault (time-boxed, about 1 hour).** Try `KICAD_CONFIG_HOME` set to a writable folder, `xvfb-run`, loading inside `kicad-cli`'s Python if it has one, and a minimal board. If it works, native `ExportSpecctraDSN`/`ImportSpecctraSES`, the zone filler and in-process DRC replace most of the custom code. If not, record the result and keep kiutils.
- **B. Write a layout specification before any more routing** (`hardware/instrument/layout/SPEC.md`): stackup (F signal / In1 GND solid / In2 3V3 pours with slow signals allowed / B signal), rules (already decided), net classes (power 0.4-0.5 mm, USB 90-ohm pair, analog), keep-outs (no digital or boost copper over the ADC and its reference; the boost loop compact on one edge), mounting holes, connector edges and directions, and the floorplan below.
- **C. Floorplan with block templates instead of force-directed placement.** Board quadrants: power entry and USB on the bottom edge; RP2040, flash and crystal in the centre-left; the ADC, its reference, the LED sinks and the head connectors in a quiet quadrant over unbroken In1 GND; the boost, the device sink and the motor drivers on the opposite edge. Inside each block, place by the data sheet's layout (RP2040 hardware design guide section 2, ADS131A04 layout example, MT3608 layout), written as relative offsets in Python. Expected effect: most nets become short intra-block routes; the autorouter only joins blocks.
- **D. Pre-route the critical nets in code and lock them** (USB pair, both crystals, the boost loop, power trunks at class width), then let Freerouting do the rest, block by block where possible, with short limits (5-10 minutes) so a failure is cheap.
- **E. In2 as power pours plus slow signals**, not a solid 3V3 plane: pour 3V3_D and 3V3_A regions on In2 under their blocks and leave channels for signals. This keeps the GND plane (the one that matters for noise) and restores a routing layer.
- **F. Scope (the user's decision, task 6):** keep one board (cheapest to assemble once) or split off a drive board (boost, plate driver, device sink, motor drivers) so the measurement board stays small and quiet. My recommendation: keep one board but lay it out with C-E first; split only if C-E still leave congestion. Board size against the price tier is already the user's decision (the 4-layer cheap tier is 50 x 50 mm, which this board will not meet either way).

## Things to keep
The decided rules (`kb/pcb_toolchain_notes.md`), the DFM gate (`mainboard.py dfm`, fails closed), netlist parity, `geometry`, the library fixes, the silk policy and the mounting-hole placer all stay useful whatever the placement method is.
